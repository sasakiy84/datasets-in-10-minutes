# 日本語スライド校正

## 適用範囲と優先順位

既存の技術・研究スライドの日本語を、読者が一読して対象と関係を理解できる文章に整える。ユーザー指定と資料固有の用語・文体を優先する。PPTXを扱うときは [master-guided-slides](../master-guided-slides/SKILL.md) の組版・描画検証も適用する。データセット紹介では [dataset-introduction-slides](../dataset-introduction-slides/SKILL.md) の事実・単位・実例の対応も確認する。

本スキルは、既存のGemini校正の提案・採否・215件の実変更対から抽出した編集基準であり、モデルの学習やファインチューニングではない。[根拠と例](references/editorial-examples.md)を参照する。適用者が本文を読み、変更ごとに判断する。単純置換や過去の提案の一括採用で校正を完了した扱いにしない。外部APIの利用を前提としない。

## 1. 校正単位と保護する情報を確定する

1. 対象資料、元版、ページ数、元ファイルのSHA-256を記録する。ページ順とPPTX内部のslide番号を照合する。
2. **必ず1ページずつ**、タイトル、全段落、表、図表のラベル、原文と訳、注記、出典を読む。必要な前提は前後のページで確かめる。変更不要のページも確認済みと記録する。
3. 引用原文、コード、ID、URL、数値、単位、版、日付、著者名、正解ラベルは保護対象とする。日本語の引用も、実データの内容なら自然さだけで書き換えない。
4. 引用と日本語の説明を区別する。要約を全文訳と呼ばず、問題文が要求する対象・順番・接頭辞などの条件を説明から落とさない。

## 2. 日本語を整える

次の順に検討し、意味に寄与する修正だけを行う。

- **主述の対応**：データ・設定・表が人の作業を行う不自然な主語になっていないか。「標準設定は〜使う」は文脈に応じ「標準設定では〜使う」とする。無条件に「は」を「では」へ置換しない。
- **助詞と数量**：「80主課題」などの過度な圧縮を「80の主課題」にする。帰着先の「へ／に」は文脈で選ぶ。「入力を〜に変換する」「集合を〜に分ける」など自然な係り受けにする。
- **修飾関係**：長い「の」の連鎖、何に係るか不明な形容を解く。「338の生成対象の部分問題」なら「生成対象となる338の部分問題」のように整理する。
- **動詞と目的語**：「除外する場合」だけで対象が不明なら、何をどの条件で除くかを明示する。並列は同じ文法単位でそろえる。
- **時制**：完了した収集・作成は過去形、手順の一般説明は現在形、現存する提供状況は「配布している」などにする。同じ説明内で理由なく揺らさず、歴史記述まで現在形へ統一しない。
- **用語と表記**：論文・データ・プログラムの改訂には原則「バージョン」。固有名や引用中の「版」は保持できる。専門語を平易にする場合も、上位／下位概念、評価指標、実装と概念の違いを保つ。
- **短く自然な文**：名詞の羅列や不自然な体言止めを必要に応じ文へ戻す。表の短い項目名は許容し、説明文と表見出しへ同じ文体を強制しない。

## 3. 意味と情報の出し方を守る

- 条件（「場合」「のみ」「少なくとも」）、論理関係（かつ／または）、主張の強さ、数え方、対象範囲を修正前後で照合する。読みやすさのために削らない。
- 分割、問題／注釈／試行、言語／文字・地域の種類、原著と現在の配布物、実際の評価モデルと表の欄名などを混同しない。
- タイトルは対象と要点を述べる。列名は表の内容を示す。必要な前提と全体像を先に、内訳や説明を後に置く。ただし具体例の後に定義を置く構成が有効なら保つ。
- 余白を埋めるための補足、既知の一般論、表から明らかな注意、重複する正解・動作説明を増やさない。
- ページ追加・削除・順序変更は理解に必要な場合だけ。文言変更と構成変更を別に記録する。
- 事実に疑問があれば、既存の一次資料・実データ・収集済みの根拠で確かめる。提案や一般知識だけで上書きしない。未解決なら断定を足さず原文を保留し、理由を記録する。日付の妥当性は実際の作業日を基準にする。

## 4. 既存提案を使うときの来歴

過去のGemini提案は候補として参照できるが、本スキルで各件を再判定する。記録には `review_method: skill_based_codex` とスキル名・版・SHA-256、実施者を記す。過去の提案を参照したページには `prior_suggestion_source: gemini-3.8-flash (cached)` とその件数を別欄に記し、今回Geminiが実施した校正と表示しない。今回の新規提案は `skill_original`、既存提案の採用は `cached_proposal_reassessed` などで区別する。新規API呼出回数は事実通りに記録する。

## 5. 変更対と判断を残す

- 各ページについて、全段落を読んだ状態、変更の有無、保護対象、構成の判断を記録する。
- 各変更はページ、段落／図形、修正前、修正後、理由、来歴を表と機械可読データに残す。
- 参照した既存提案には採用・部分採用・見送りを明示する。事実確認・構成判断は文言の対と分けて理由を残す。
- 実際のPPTX差分と記録を照合する。先行試行の変更を引き継ぐ場合は、その来歴を今回の変更と区別する。

## 6. 表示と成果物を確認する

元のマスター、編集可能な文字・表・図、出典、配色を維持する。通常タイトルは1行に収める。本文の少数文字の折返しだけを理由に短縮や縮小をしない。文字の欠落・重なり・はみ出し、表の行高・列幅・罫線・表注との間隔を確認する。グラフの語を変えた場合はキャッシュと元の埋込データをそろえる。

複数文・複数行にわたる説明は、助詞や述語を補った通常の文章にし、左揃えで読む。分析対象の切替を説明するページでも、本文に文量がある場合は通常の本文ページとして見出しと説明を配置する。表紙の副題や短い章扉の中央配置は、その役割に合わせて保つ。

最終PPTXからPDFを出力し、ページ数、変更文言の存在、OOXMLと参照関係を検査する。全体の一覧と変更ページの拡大描画で確認し、問題があれば修正・再出力して再確認する。記録とPPTX・PDFのハッシュを対応させ、データセットごとのコミットなどユーザー指定の単位で保存する。未実施の検査を実施済みと記載しない。
